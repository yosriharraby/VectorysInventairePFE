Chapitre 5 — Tests et validation

Ce chapitre présente la démarche de vérification de Vectorys Inventaire. Après la réalisation technique (chapitre 4), il s'agit de démontrer que les fonctionnalités critiques — authentification, import Excel, comptage avec quotas, synchronisation hors ligne, détection d'écarts et consultation KPI — se comportent conformément aux exigences du chapitre 2. La stratégie privilégie des scénarios reproductibles, des jeux de données contrôlés et une validation multi-canal (API, web, mobile).

Introduction

Dans un contexte logistique, une erreur de comptage ou d'assignation a un coût métier immédiat. Les tests ne se limitent donc pas à « l'API répond 200 » : ils vérifient les transitions de statut (EN_ATTENTE → EN_COURS → TERMINE), le respect des quotas US, l'isolation des emplacements par agent et la cohérence des données en base SQL Server.

La campagne de validation s'appuie principalement sur des tests d'intégration et bout-en-bout manuels, assistés par Swagger, Postman, SSMS et un guide opérationnel (scripts/GUIDE-TEST-IMPORT.txt). Ces approches sont complétées par la documentation OpenAPI et, côté Flutter, une base de tests unitaires destinée à être enrichie.

5.1 Stratégie et niveaux de test

La pyramide de tests adoptée pour le projet est volontairement pragmatique : fort accent sur les scénarios métier traversant plusieurs couches, faute d'une suite unitaire exhaustive à ce stade du stage.

Chaque scénario formalise : préconditions, étapes, résultat attendu et critère de succès. Les anomalies détectées sont corrigées avant de basculer vers le sprint suivant (définition de « Done » Scrum).

5.3 Tests d'API (Swagger et Postman)

Les tests d'intégration API valident le contrat HTTP indépendamment de l'interface graphique. La procédure type est la suivante.

  1. Obtenir un JWT superviseur via POST /api/auth/login (email + mot de passe).
  2. Créer un inventaire (POST /api/inventaires) et noter inventaireId / passageC1Id.
  3. Importer le stock (POST /api/passages/{id}/import-stock, multipart).
  4. Vérifier GET /api/emplacements?passageId=….
  5. Obtenir un JWT agent (code personnel) et appeler GET /api/emplacements/mes-emplacements.
  6. Enregistrer des scans (POST /api/scans) jusqu'à TERMINE.
  7. Déclencher POST /api/ecarts/detecter/{inventaireId} puis consulter la liste.
  8. Interroger GET /api/kpi/dashboard avec filtre inventaire.

5.4 Scénario bout-en-bout : import et comptage

Le scénario nominal de recette reprend le guide d'import/scan. Il constitue le test E2E principal du projet.

Objectif. Vérifier qu'un inventaire créé côté superviseur peut être compté correctement par deux agents distincts, avec auto-terminaison et isolation des tâches.

5.4.1 Procédure

  1. Démarrer l'API et contrôler Swagger (http://localhost:5000/swagger).
  2. Superviseur : se connecter, créer un inventaire, importer test-import-stock.xlsx.
  3. Contrôle SQL : les emplacements TEST-* sont associés aux bons CodePersonnel.
  4. Agent AG001 : ne voit que TEST-A01 et TEST-A02 ; scanne TEST-A01 jusqu'à TERMINE (US-T001×2 puis US-T002×1) ; un scan supplémentaire est refusé.
  5. Agent AG002 : ne voit que TEST-B* ; termine TEST-B01 et TEST-B02 selon quotas.
  6. Contrôle SQL final : statut TERMINE et nombre de scans cohérents avec les quantités théoriques.

5.5 Tests mobile, offline et supervision

5.5.1 Mode hors ligne

Le test offline simule une coupure réseau pendant la boucle de scan :

  1. Activer le mode avion (ou couper le Wi‑Fi) après ouverture d'un emplacement.
  2. Scanner plusieurs US : les enregistrements doivent rester en file SQLite locale.
  3. Rétablir le réseau : synchronisation automatique ou manuelle via POST /api/scans/batch.
  4. Vérifier l'absence de doublons côté serveur et la mise à jour des statuts d'emplacement.

T-OFF-02Retour réseauSync réussie ; bannière à jourOK
T-OFF-03Re-sync accidentellePas de double comptage serveurOK

5.5.2 Supervision et KPI

Côté web, la validation porte sur :

  • le suivi temps réel (SignalR / endpoint de suivi) pendant les scans agents ;
  • la détection d'écarts après terminaison C1 et le déclenchement de la branche A ;
  • l'affichage du dashboard KPI (précision, performance, qualité, WMS) pour l'inventaire de test.

5.8 Synthèse des résultats et limites

5.8.1 Bilan

  • Le chemin critique C1 (création → import → scan → TERMINE → contrôle BDD) est validé de bout en bout.
  • La séparation des rôles et l'assignation par CodeAgent sont stables.
  • Le mode offline et les KPI de base répondent aux besoins de démonstration et de pilotage.
  • La branche A (recomptage ciblé) a été vérifiée via API et interface écarts.

5.8.2 Limites assumées

  • La couverture de tests automatisés unitaires reste partielle : la valeur immédiate a été placée sur les scénarios d'intégration et E2E, plus représentatifs du métier terrain.
  • Les figures de déploiement LAN (portail et APK pointant vers l'IP serveur) seront consolidées lors de la mise en service locale (cf. placeholders 4.17 et 4.18).
  • Certains indicateurs KPI restent partiels faute de données métier riches (valeur monétaire, occupation WMS maximale, etc.).
Ces limites n'invalident pas la recette du cœur fonctionnel : elles orientent plutôt les travaux post-rapport (automatisation, durcissement S6/S8, déploiement serveur local S9).

Conclusion

Ce chapitre a formalisé la stratégie de test de Vectorys Inventaire : environnement contrôlé, jeux de données Excel reproductibles, batterie de cas API, scénario E2E import/comptage, validation offline et supervision KPI, matrice de couverture des RF et revue non fonctionnelle. Les résultats montrent que le cycle inventaire multi-canal est opérationnel pour une exploitation en conditions de démonstration et de déploiement local. Les perspectives d'évolution (automatisation accrue, finalisation des workflows de clôture/export, mise en production sur serveur d'entreprise) seront reprises dans la conclusion générale du rapport.
